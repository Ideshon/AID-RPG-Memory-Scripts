# Аудит Memory Engine и Universal RPG — 8 ноября 2026

Проверяемые версии: Memory Engine 1.8.0 и Universal RPG 2.33. Проверка охватила восемь игровых вкладок, общие функции состояния, импорта, карточек, подтверждения памяти, календаря, контекста и механических изменений. Ни статический анализ, ни AID-Sandbox не доказывают отсутствие ошибок на сервере AI Dungeon. Ниже отдельно отмечены воспроизведённые проблемы и области, которым нужна дополнительная проверка.

## Результаты текущего исправления

- `adopt` сохраняет исходные тип, ID, название, Notes и ключи; данные памяти и связанная Story Card существуют одновременно.
- `cards show` показывает активную карточку; `cards repair` восстанавливает исходный тип существующих управляемых карточек; `restore` возвращает исходник. Удалённую карточку можно восстановить с новым ID. При вручную изменённом маркере операция останавливается.
- Явная связь `cards link INDEX | TYPE | ИМЯ` направляет источник в существующую запись. Она не удаляет и не объединяет ранее созданные записи с разными именами. При совпадающем имени импорт RPG и импорт персонажа и раньше использовали один ключ памяти.
- Custom-карточки импортируются в факты без угадывания смысла типа. «Летопись» остаётся Custom-фактом, а не автоматически созданным событием; «Отношения» не превращаются автоматически в направленные связи между персонажами.
- Передача Custom сохраняет тип, все триггеры и переносы текста. После передачи `edit fact ID` меняет эту же Story Card. Служебный экспорт RPG исключён.
- Связанные Custom-факты защищены от удаления обычной и пакетной командами и от вытеснения новыми фактами при заполнении лимита.
- Обработчики, используемые только Context и Output, перенесены в соответствующие вкладки. Library и Input проходят проектный предел 100 КиБ каждый. Это локальный запас проекта, а не подтверждённый универсальный лимит платформы.

## Проверки и их ограничения

1. Новый `tests/test_cards_v180.js`: сохранение метаданных при замене объекта API, исправление регистра типа, явная связь разных названий, отсутствие второй карточки, Custom-синхронизация, исходное восстановление, удалённая карточка, отказ API, изменённые Notes между предпросмотром и подтверждением, конфликт дубликатов, защита фактов при заполнении лимита.
2. `node --check` для четырёх изменённых вкладок; AID-Sandbox `where` и `play --turns 3` для обоих комплектов. Прогон обычных ходов не заменяет новый целевой тест карточек.
3. Старые тесты Memory запускаются через `tests/run_legacy.js`: пять наборов импорта, подтверждения памяти, отладки, RPG-моста и переносов проходят с адаптацией старых ожиданий версии. Общий `test.js` доходит до проверки reset-preview и останавливается: тест не учитывает добавление `config.calendar` при миграции старого состояния. Это не доказательство успешности оставшейся части набора.
4. Из 29 исторических наборов RPG прошли 19. Десять остановились: `test.js`, `test_framed_setup.js`, `test_v210.js`, `test_v211.js`, `test_v221.js`, `test_v224_batch.js`, `test_v225_templates.js`, `test_v226_maintenance.js`, `test_v28.js`, `test_v29.js`. Часть ожидает удалённые команды заметок и старые buff; финансовые и шаблонные различия требуют отдельного разбора, их нельзя объявлять безвредными.
5. Новые проверки карточек используют доступный в песочнице контракт API с заменой объекта. Причина исчезновения карточки в интерфейсе по одному сообщению не доказана: изменение регистра типа — найденный риск, для которого добавлены сохранение исходного типа и repair. Нужна проверка в живом приключении.

## План дальнейших исправлений

### 1. P1 — сохранить неизвестные версии RPG без сброса

**Подтверждено.** В `AID_Universal_RPG/Scripts/Library.js`, функция `rpgInit`, условие `version !== 1` создаёт новое состояние. Воспроизведение с `state.rpg={version:999,marker:'SAVE'}` теряет исходную запись после `rpgInit()`.

Исправление: отдельно обрабатывать отсутствие состояния, поддерживаемую старую версию и неизвестную версию. Для неизвестной версии показывать диагностический текст и сохранять исходный объект. Только явный reset может очистить его. Все четыре хука должны одинаково обрабатывать отказ миграции.

Критерии: неизвестная версия и повреждённое состояние не теряют данные; поддерживаемые старые состояния мигрируют один раз; обычное новое приключение создаётся без ошибки.

### 2. P1 — запретить служебные имена в RPG-таблицах

**Подтверждено.** `rpgApplyDelta` допускает предмет `constructor`: после `{items:[{name:'constructor',qty:1}]}` у `r.items` появляется собственный служебный ключ. Аналогичные таблицы навыков, характеристик и шаблонов требуют прохода по всем местам записи.

Исправление: единая проверка имени и собственных ключей, исключение `__proto__`, `constructor`, `prototype`; безопасное чтение числового количества и конечности результата. Сохранить совместимость обычных русских названий. Не менять прототип сохранённых объектов без миграции.

Критерии: вредные и унаследованные имена не меняют состояние; дробные/отрицательные/нечисловые количества обрабатываются по правилам каждой операции; обычный инвентарь не меняется при миграции.

### 3. P1 — соблюдать общий бюджет контекста

**Подтверждено.** RPG Context при `maxChars=5000`, `memoryLength=6000` и входе 7000 символов вернул 8202 символа. Ограничивается история, но не сумма защищённой памяти и механического блока. Memory Engine также необходимо проверить при уже переполненном контексте от другого скрипта.

Исправление: определить приоритеты защищённой памяти, текущей механики и истории; проверять итоговый размер; сокращать дополнительные блоки до вставки. При бюджете меньше обязательной памяти давать наблюдаемую диагностику. Проверить оба порядка обработки Context двух независимых скриптов.

Критерии: 0/малый/обычный бюджет, отсутствующий `memoryLength`, переполненная память, длинный инвентарь; итог не превышает согласованный бюджет и сохраняет текущие результаты броска.

### 4. P1 — согласовать undo с управляемыми карточками

**Подтверждено как ограничение текущей реализации.** `amUndo` восстанавливает базу и очищает очередь, но не возвращает Story Cards. Это явно написано в его ответе, однако после undo рассказчик может продолжать читать отменённые данные.

Исправление: после отката пересчитывать очередь для затронутых управляемых карточек; безопасно обрабатывать исчезнувшие записи, Custom-факты и отказы API. Не удалять ручные карточки. Связи и резервные копии должны пережить откат без осиротевших записей.

Критерии: изменение → синхронизация → undo → синхронизация возвращает согласованный текст; отказ API сохраняет очередь; операция восстановления ручной карточки не отменяется случайным undo.

### 5. P1 — не терять дополнительные сведения при переносе между приключениями

**Подтверждено по составу экспорта.** `amTransferScopeData` переносит сущности и факты, но дополнительные строки находятся в `cardAdoptions.extra` и в portable-пакет не входят. Сами ID карточек нельзя переносить как связи в другое приключение.

Исправление: включить дополнительные сведения в переносимую часть канонической записи, не копируя чужие ID и резервные копии карточек. Ввести совместимый формат/миграцию. Уточнить перенос режима календаря и относящихся к нему настроек.

Критерии: все активные исходные сведения сохраняются при all/world в разрешённой области; импорт в другое приключение создаёт новые местные связи; старые portable v1 продолжают читаться.

### 6. P2 — разделить ключи имён и сравнение полного текста

**Подтверждено по коду.** `amKey` обрезает строку до 110 символов, но `amFact` использует его для сравнения текста фактов длиной до 380. Разные факты с одинаковым началом могут считаться дубликатами. `amReviewKey` обрезает значение до 500 и требует аналогичного анализа для длинных биографий.

Исправление: отдельная нормализация полного текста без обрезания, стабильный ключ или сравнение полного нормализованного значения. Не менять ключи уже существующих сущностей. Проверить импорт заметок RPG и повторное подтверждение предложений.

Критерии: два факта с одинаковыми первыми 110 символами и разными концами сохраняются; точный повтор не создаёт новую запись; изменение конца длинной биографии не теряется.

### 7. P2 — явно определить владение датой, местом и описанием героя

**Подтверждено как политика, способная давать устаревшие сведения.** `amRpgPayload` заполняет только пустые поля персонажа; место `at` также заполняется лишь при отсутствии. Повторный импорт нового снимка не обновляет эти непустые поля. Отдельный RPG-снимок и карта персонажа могут расходиться.

Исправление: описать владельца каждого поля; хранить происхождение и признак ручной правки. При необходимости обновлять RPG-поля только если пользователь их не переопределял. Не смешивать условный RPG-календарь по 30 дней с реальными датами Memory. Связь Story Card не должна тайно переименовывать героя в RPG.

Критерии: новое место в RPG отражается согласно выбранной политике; ручной текст защищён; календарь off остаётся off; переименование героя имеет явный сценарий связи и не создаёт неожиданный дубль.

### 8. P2 — управлять устареванием дополнительных строк

**Известное ограничение.** Сопоставление исходной карточки со структурированными полями текстовое. Строка «Фрилансер художник» и поле «Фрилансер» частично повторяются. Дополнительная строка с возрастом или работодателем сама не понимает, что факт изменился; скрытая как повтор строка может снова появиться при изменении поля.

Исправление: переносить распознанные сведения в предложения по конкретным полям с указанием источника; оставить произвольные строки редактируемыми. Не угадывать пол, профессию, событие и отношение только по номеру строки. Согласовать окончательное удаление строки и её перенос в поле.

Критерии: изменение профессии не возвращает старую профессию из extras; удалённая строка не появляется после повторного импорта; пользователь видит, откуда взялся каждый факт.

### 9. P2 — восстановить воспроизводимую систему тестирования

**Подтверждено запуском.** Исторические тесты читают хуки из `tests/`, фиксируют старые версии и удалённые команды. Временный адаптер пути и ожиданий версии помогает проверке, но не заменяет обновление тестов.

Исправление: единый runner с путём `Scripts/`, версия из текущего build, отдельные fixtures для миграций; разделить тесты актуального поведения и тесты старых контрактов. Для десяти отказов RPG завести отдельные решения: устаревшее ожидание или реальная регрессия, особенно финансы и шаблоны. Исправить Memory reset fixture до проверки неизменности preview.

Критерии: один документированный запуск без копирования файлов, без скрытой замены исходника теста; все актуальные тесты зелёные; отклонённые исторические ожидания перечислены и объяснены.

### 10. P2 — модули исходников и контролируемая сборка

**Подтверждено размером файлов.** RPG Library занимает 266954 байта, а Memory Library/Input близки к проектному пределу. Успешный запуск в Node не подтверждает допустимость размера на платформе.

Исправление: исходные модули состояния, карточек, импорта, команд, интерфейса и механик; сборка в прежние четыре JS-вкладки. Сборка должна проверять синтаксис, отсутствие дублирующих объявлений, версии всех вкладок, лимиты размеров и детерминированность. Сначала выделить чистые функции без изменения state-контракта. Независимые Adventure Scripts не использовать как способ разделить одну базу без отдельного протокола обмена.

Критерии: одинаковый вход сборки даёт одинаковые четыре файла; сохранения и команды работают как прежде; доступен один комплект установки, карта исходных модулей и тест полного собранного экспорта.

## Порядок выполнения и проверка на платформе

Сначала задачи 1–3 и актуальная тестовая инфраструктура; затем 4–7; после них 8 и модульная сборка. Каждая поставка получает новую версию и описание поведения в журнале. Изменения состояния требуют fixtures старых сохранений.

В живом AI Dungeon проверить сначала одну резервируемую Character-карточку, затем Custom «Записка»: видимость после adopt, исходный тип, ID, Notes, триггеры, обновление после изменения памяти и restore. Повторить с обоими порядками подключённых RPG/Memory. Проверить, что служебная команда не расходует игровое время и не продвигает сюжет. Эти проверки ещё не выполнены человеком для 1.8.0.
